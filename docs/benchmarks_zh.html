已落地（f475966）：LTO 链接现为 siluc 默认——rt.o 改存 LLVM bitcode（一次性 0.15s），用户模块同编 bitcode，链接 clang -flto -O2 -Wl,-dead_strip（无冲突）。成本账：每次链接 +20ms（0.05 vs 0.03s），siluc 总时长温态维持 0.11-0.12s。收益 （安静环境手测，vs Rust）：spectral 4.66→4.15ms、fib 1.08×、 dict 1.04×、arith 1.03×；启动基线减半（4.1→2.1ms）。 首次集成失败的两个教训：诊断须用 rt-lifted.ll（internal global 已提升），spectral 跨分钟摆动 4.15-6.8ms 使套件轮均值 不可作单一依据（三轮 0.9×→0.7×→0.8×，binary 与 rust 双侧 同抖）——单项手测 A/B 是本机可靠口径。 两块已归因的剩余短板见第三节。

三、速度演进轨迹（做对了什么）

日期 里程碑 jsonparse 全套几何 vs Rust

10-25dead_strip 链接（体积 3×↓）——
10-25match 类模式窄化：case JInt(n) 载荷静态绑定78→75ms—
10-25str 传参借用：修复每层递归深拷整个文档78.7→8.3ms（9.5×）—
10-25刷新报告（含全部修复）10.7ms（0.4×）0.9×（持平区间）

两个已归因的剩余短板（按需再战）：

  • jsonparse 0.6×（10-27 第三轮：8.0-8.5ms vs rust 4.5-4.8ms，物化池化后）：

三层归因（构造 12% / 物化大头）与修复链——v1.11.4 的池最初挂在了 零调用的 rawstr_char_at 上（收益 0.8ms 实为噪音，本轮修正）；真正的 热路径是 s[i] 的 view→RAWSTR 物化（rawstr_new_copy：2 次 malloc + memcpy + SIMD 码点计数，每字符 ~62ns）。本轮把物化接到 rawstr_char1（单字节码点走 256 项共享池，cap=-1 永生哨兵）： 扫描探针 9.9→4.7ms，**与手写 ord() 惯用法持平（62→~5ns/字符）**， jsonparse 9.8→8.0-8.5ms。内联策略实测否定：clang -O2 早已内联 小运行时函数（汇编证实），剩余单次 char1 调用加 alwaysinline 反而 4.64→4.91ms（icache 伤）。**剩余差距 ≈ 构造成本 1.9ms （纯运行口径 5.2 vs 3.5ms 差 1.7ms）**——sum-type（RFC S1-S4）从 "次要" 升级为收官关键路径：物化修复后构造占比从 12% 升至 ~24%。

  • wordcount 0.6×（10-27 复测）：v1.11.3 的下标类型推断消除了

w = vocab[i] 的 pyobj 装箱（.ll 调用序列验证），但暴露了更深 一层：rawlist_str_get 是拷贝语义（slots own copies），每次 读取 malloc 新块 + free 旧槽，两次堆操作反而贵过单次装箱。 A/B 实测（旧 .ll 21.2ms vs 新 24.3ms，各 15 次取最小值）。 根治 = 借用读（不可变元素下标返回借用指针）或缓冲复用 （rawstr_copy_into，Rust clone_from 思路）——与 jsonparse 的 字符访问是同一族不可变值拷贝语义问题，可一并治理。

四、方法学要点

  • 四平面先验证后计时：每个程序先确认解释器/CPython/编译

产物/Rust 孪生四方输出一致，否则该行标记 MISMATCH 不计。

  • CPython 平面经 pycompat 垫片（Silu 类的位置构造器与裸

CPython 语义不同）；Rust 孪生逐程序手工镜像并比对输出。

  • 编译计时中位数 3 次；启动基线单独扣除参照（4.3ms silu /

2.3ms rust 空程序）。

  • 逐项归因采用 ablation + macOS sample 采样（示例：jsonparse

的 70ms 热区被采样锁定为传参深拷贝，修复后 8.3ms）。
